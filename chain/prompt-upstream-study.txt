Ты — дозорный апстрима в форке `gpt-mem/opencode-mem` (линия `main`). Задача сессии: разобрать новый релиз апстрима и подготовить разбор для человека.

## Вход

- `$UPSTREAM_TAG` — тег апстрима, который разбираем (например `v2.0.33`).
- `$UPSTREAM_COLLECTED` — JSON с сырьём: список коммитов диапазона, связанные PR, изменённые файлы, список наших файлов расхождения.
- `$UPSTREAM_POLICY` — профиль продукта форка (что держим, что не держим, какие файлы обязаны остаться).
- `$UPSTREAM_OUT_DIR` — каталог для артефактов (создай, если нет).
- `GH_TOKEN` — токен GitHub (в окружении, не выводить его в ответ).

Если `UPSTREAM_DRY_RUN=1` — **ничего не пиши в GitHub**: issue не создавай и не комментируй, PR не открывай. Отчёт всё равно пиши в `$UPSTREAM_OUT_DIR/report-$UPSTREAM_TAG.md` и выведи `ISSUE=0`.

Если `$UPSTREAM_COLLECTED` не существует или в нём нет поля `commits` — остановись и напиши: «НЕТ СЫРЬЯ» (детектор не нашёл нового релиза). **Детектор сам не запускай** — это работа этапа collect, иначе ты потратишь токены на повторный разбор и придёшь к другим выводам, чем порт. Выведи `TAG=$UPSTREAM_TAG`, `ISSUE=0`, `REPORT=` (пусто) и закончи.

## Что нужно сделать

1. Прочитай `$UPSTREAM_COLLECTED` и `$UPSTREAM_POLICY`.
2. Разложи изменения диапазона по трём классам:

   - **PORT** — берём в порт в форк. Это изменения ядра/CLI/TUI/сервера/SDK/плагинов, баги, производительность, экономия токенов, безопасность. Не тяни в порт то, что относится к нативному приложению, вебу, публикациям и сайтам.
   - **ASK** — требует решения человека: изменение задевает файл, в котором форк разошёлся с апстримом (список таких файлов — поле `our_diverged_files` в JSON и `touches_our_divergence` у коммитов), либо задевает наши обязательные файлы (`must_keep`), либо задевает то, чего у нас быть не должно (`must_not_return`). Сюда же — всё, что меняет схему БД или миграции.
   - **SKIP** — мимо: файлы из `skip_paths` профиля (нативное приложение `packages/app`, `packages/desktop`; веб `packages/web`, `packages/session-ui`, `packages/gui-extensions`; сайты, статистика, публикации), релизные и шумовые коммиты по `skip_message_patterns`, пакеты вне `port_scopes`.

   Считай по фактам из JSON (файлы коммита, PR), а не по догадкам. Если коммит тянет и PORT, и SKIP-файлы — он ASK.

3. Напиши отчёт на русском в `$UPSTREAM_OUT_DIR/report-$UPSTREAM_TAG.md`. Структура:

   ```
   # Апстрим <tag> → наш форк (gpt-mem/opencode-mem, main)

   - Апстрим: <upstream_repo> @ <sha12>
   - База форка: <base sha12>
   - Коммитов в диапазоне: N (разобрано M)

   ## Итог
   | Класс | Коммитов | Что значит |

   ## Наш профиль
   (коротко: что держим — терминальный агент без нативного приложения и без веба,
   экономия токенов усечением вывода + компактификацией, наши фишки; чего не держим)

   ## PORT — что берём в порт
   | PR | Коммит | Что | Почему | Файлы |

   ## ASK — на решение человека
   | PR | Коммит | Что | Почему | Файлы |

   ## SKIP — мимо
   | PR | Коммит | Что | Почему |

   ## Как портировать
   1..3 — что делает этап 2 (сборка порта) и что остаётся за человеком.
   ```

   Для PR используй формат `[#123](url)` и название PR из JSON.

   **Как писать отчёт.** Таблицы **PORT** и **ASK** — полные, по строке на каждый коммит
   (это идёт дальше в сборку порта). SKIP можно свернуть в группы по теме («веб: N
   коммитов», «релизы и шум: N»), но PR-ссылки сохрани.

   **Пиши файл по частям.** Первый вызов — `write` с шапкой, «Итог» и «Наш профиль»; дальше
   добавляй разделы отдельными вызовами (`edit` с якорем или `bash` с `cat >> file <<'EOF'`).
   Один вызов с десятками КБ текста обрывается по лимиту вывода: аргументы инструмента не
   догружаются, вызов не выполняется вовсе — и сессия падает на ровном месте.

4. Создай issue в форке `gpt-mem/opencode-mem`:
   - заголовок: `chore(upstream): порт <tag> — <N> в порт, <M> на решение`;
   - тело: отчёт + раздел «Решение по классу ASK» (по пункту на каждый ASK: «тянуть / не тянуть») + чек-лист;
   - **если issue с таким же заголовком уже есть** — не создавай второй, а добавь комментарий с обновлённым разбором (ищи через `gh api search/issues --method GET -f 'q=repo:gpt-mem/opencode-mem is:issue in:title "<заголовок>"'`, сверяй заголовок целиком). Если разбор не изменился с последнего комментария — новый комментарий не пиши, просто сошлись на существующий issue;
   - тело issue пиши только через файл (`--body-file`), в команде с обратными кавычками тело не выживает;
   - issue создаётся в форке, но **закрывать его не надо** — closing-ключевые слова на этой линии не применяются.

5. Выведи в конце ровно три строки (их заберёт пайплайн):

   ```
   TAG=<tag>
   ISSUE=<номер issue>
   REPORT=<путь к отчёту>
   ```

   Плюс короткий человеческий абзац: сколько в порт, сколько на решение, сколько мимо, и одна фраза — что здесь самое важное для нашего продукта (например, где апстрим помогает экономить токены или где ломает терминальный режим).

## Ограничения

- Ничего не коммитить, не пушить, не мержить, не создавать PR — это делает следующий этап.
- Репозиторий форка не править. Работаешь только с отчётом и issue.
- Секреты не выводить. `GH_TOKEN` не печатать.
- Не выдумывать PR и файлы: только то, что есть в JSON. Чего в JSON нет — помечай как «не разобрано» и скажи об этом в итоговом абзаце.
