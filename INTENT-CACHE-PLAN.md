# Стратегия сжатия: два трека + интент-ориентированная компактация

Дата: 2026-10-10. Источник: разбор замеров + идеи Вовы. Статус: реализуется (B0 GO, IntentTracker день 1+2 смержены, следующий — UNIFIED-MASK ledger, issue #29).

## Данные, на которых строим

- На `opencode-go/mimo-v2.6-flash`: cache read ≈ **2.2%** от цены uncached input (**~45×**). Замерено issue #9/#20.
- Mid-turn компакт меняет префикс → кеш обваливается: −45% токенов, но **+70% стоимости** (бенчмарк sess_...32dc09fa vs ...e8646771).
- Уже сделано по кешу: PR #21 (компакт на batch-границе), PR #22 (sliding window, `OPENCODE_MEMORY_MIDTURN`), issue #23 (compact-at-first-delivery, P0).

## Инсайты

1. **Стоимость токенов неоднородна.** Закешированные (старые) в ~45 раз дешевле свежих. Оптимум для платных моделей: стабильный префикс, прирост только в хвост.
2. **Мусорный контекст вредит и качеству**, не только кошельку — дребезжит внимание модели. Сжатие полезно независимо от кеша.
3. **Для бесплатных моделей кеш-эффекта нет** — сжатие работает как раньше, без оглядки на префикс.
4. **Сжимать = заменять файлы рефами + ретрив** (наша SQLite + get_tool_call_details) — это уже реализовано и правильно по механике.
5. **Граница сброса кеша — естественный момент для компактации.** Если юзер сменил суть задачи — новый префикс и так начинается, сброс бесплатен.
6. **Если цель юзера не меняется** — приращаем хвост, кеш дешёвый; резать середину можно, но это уже вопрос качества, не денег.
7. **Ключевая идея: компактация по ИНТЕНТУ, а не по заполненности контекста.** На каждом provider-шаге дешёво проверяем: «изменилось ли направление задачи от текущего интента?»
   - не изменилось → просто приращаем хвост (кеш работает сам)
   - изменилось → «закрываем» интент: вырезаем смежный контекст старой темы в нашу storage, открываем новый префикс-отрезок
8. **Несколько интентов живут параллельно** в рамках сессии/проекта. На старте сессии определяем, какой из них юзер продолжает.
9. **Интент = дешёвая строка-саммари** (3 предложения: что за задача юзера) — это наш «кеш» в смысле быстрого восстановления контекста.
10. **Опционально: UI-подтверждение** («тема задачи сменилась?» да/нет/поясни связь) — для ботов и интерактивных клиентов.
11. **Вопрос-проверка на старте дешёв сам по себе** — идёт через того же провайдера и греет его же кеш.

## Трек A — сжатие без учёта кеша

Для: бесплатные модели, кеш-free провайдеры (Groq, Cerebras, free-tier), fallback.

Состояние: **готово к продакшену** (MemoryContext, маркеры с call_id/retrieve, PII-теги, 25+ тестов, CI).

Доделать:
- A1: авто-детект маршрута — если у провайдера нет cache-метрик в usage → включать MEM по умолчанию
- A2: документировать: на кеш-free маршрутах MIDTURN-окно можно открывать без оглядки на стоимость
- A3: бенчмарк-сценарий «multi-turn coding без кеша» — подтвердить качество (не только токены)

## Трек B — интент-ориентированное сжатие (кеш-провайдеры)

Для: платные модели с prefix-caching (mimo, Anthropic, OpenAI, DeepSeek...).

Фазы:
- **B0 (в работе)**: compact-at-first-delivery (issue #23) — компактить только ещё не отправленное. Это база, даёт первые реальные доллары.
- **B1**: IntentTracker — на каждом provider-шаге дешёвая проверка смены направления: маленькая модель (`ladder/explore`/`service:classify`) или embedding-косинус к текущему intent-summary. Порог: cosine < T → смена.
- **B2**: `IntentRecord` в нашей SQLite: `(intent_id, session_id, summary(3 предложения), status active|closed, started_at, closed_at, parent_intent)`.
- **B3**: на смене интента — финализация старого: вырезка смежного полезного контекста (tool-выводы старой темы) в storage, маркеры остаются; новый префикс начинается с summary-интента.
- **B4**: восстановление — при возврате к старому интенту («а вернёмся к X») рефреш summary из storage + ретрив по маркерам по надобности.
- **B5 (опционально)**: UI-подтверждение смены темы для ботов.

## Метрики успеха

- Трек A: токены −N% к baseline, retrieval-success не хуже baseline.
- Трек B: **стоимость за сессию ≤ stock-baseline** при токенах −30%+; cache-hit на stable-intent отрезках не падает; ответы-needle находятся в 100% прогонов.
- Замерять только через agent-benchmarks (`benchmark run --opencode-session`), сравнение MEM-on/off на идентичных сценариях.

## Стратегия веток

Изменения делим по отношению к prompt-cache:

- **cache-safe** (основная линия `memory-context-v1`): всё, что не мутирует уже отправленный префикс — compact-at-first-delivery (B0), ретрив-тулы, PII, маркеры, Tracker интентов, storage. Эти изменения можно мержить спокойно.
- **cache-breaking** (отдельная ветка `cache-breaking-experiments`): mid-turn компактация, sliding-window, любые правки истории после отправки. Живут отдельно, включаются флагами (`OPENCODE_MEMORY_MIDTURN` и т.п.), в основную линию попадают только как выключенные по умолчанию опции или после пересмотра в свете трека B.
- Мерж в `memory-context-v1` cache-breaking изменений — только с явной пометкой в PR: «cache-breaking, флаг off by default».

Groomer при чистке обязан проверять: если в рабочем дереве/ветке есть изменения, мутирующие историю после отправки — это ветка `cache-breaking-experiments`, не в основную линию.
