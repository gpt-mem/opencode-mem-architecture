## Почему форк не работал у пользователя (два независимых дефекта)

**Дефект 1 — канал сборки.** `packages/cli/src/database-path.ts` берёт `opencode.db` только для каналов `latest|dev|beta|next|prod`, иначе `opencode-<канал>.db`. Скрипт сборки канал не задавал, `packages/script/src/index.ts` выводил его из имени ветки → `v2-base` → `opencode-v2-base.db`. Форк открывал параллельную пустую базу: креды пусты, 161 сессия не видны, `mem-gpt/build` → 401 (заголовок `Authorization` не уходил вообще). Лечится `OPENCODE_CHANNEL=latest` в `run-build.sh` + гейтом в `run-selftest.sh`/`run-releaser.sh` (путь БД и список кредов кандидата обязаны совпасть со стоком).

**Дефект 2 — неидемпотентная миграция.** `20261019172723_colossal_sue_storm` создавал `provider_cache_mark` без `IF NOT EXISTS`; таблица осталась на боевой базе от удалённой миграции `20261011014246_damp_diamondback` (её id не записан) → `table provider_cache_mark already exists` → форк не открывал базу вообще. Лечится `CREATE TABLE IF NOT EXISTS` + регрессионным тестом.

## Закрыто в этом цикле

### A. Маска Ladder: второй шаг ассистента умирал (gpt-mem/opencode-mem#160) — исправлено

`Error: invalid ladder_cache_variant` на каждом ходе с `ladder/*`, который делает вызов тула.

**Истинная причина (не «протухший scope»).** Маска слала блок `ladder_cache_variant`; сервис проверял его против состояния, которого клиент не видит, и обе проверки падали всегда:

- `rung` должен входить в `rungsFor(config, body.model)` — статический список ладдера, а сервис отдаёт в `x-ladder-model` rung из динамического пула free-моделей (этих id в `config/ladders.json` нет);
- `cache_scope` должен совпадать с `cacheScopeFor(env, rung, key, conversation)` сервиса, а scope = `SHA-256(model, key, conversation)` — ключ пула ротируется, разговор растёт, поэтому scope клиента не совпадает никогда.

Scope был свежий (выдан предыдущим ответом за секунду до) и всё равно отвергался; подставной `v1_<32 hex>` — тоже. Матрица замеров на снятом теле форка: с блоком → `400`, без блока → `200`; подмена scope/variant/rung/messages внутри блока → по-прежнему `400`.

**Что сделано:**

- `gpt-mem/opencode-mem#165` — маска и леджер `provider_cache_mark` выпилены из форка, `ladder/*` уходит на штатные маркеры v2 (`[showing lines 2976-3000 of 3000; full output saved to <path>]` — полный вывод лежит на диске). Merge `7a12f66b4abc741d380af2125ef9fe4e72d43f53`.
- `trained-assist/trained-assist-llm-ladder#276` — сервис больше не отвергает легаси-блок: поле вырезается, отдаётся дефолтная ветка. Смержено и задеплоено.
- `trained-assist/trained-assist-llm-ladder#277` — разбор, почему протокол был неработоспособен, и требования к рабочему контракту (scope по кэшированному префиксу, а не по разговору; проверка rung по эффективному набору; подсказка не должна ронять запрос; клиент должен видеть обслуженную ветку и её cache-usage) + измеренная экономия: cache read ≈ 2.2 % цены uncached-инпута, а компактирование внутри хода = −45 % токенов и **+70 % цены**.

**Проверено на новой сборке `7a12f66b4abc`:** селфтест `T1–T5 exit=0` (раньше T1–T3 падали), в запросе нет блока (`hasVariant=false`), все ответы `200`, префикс-кеш ладдера работает сам (`x-ladder-attempts: …, pin=hit`).

**Про сжатие:** рабочие инструменты на месте — штатное усечение v2 (2 КиБ / 2000 строк, полный вывод на диск, retention 7 дней) и сессионная компактификация. `OPENCODE_CACHE_MASK=0` в `~/.zshrc` оставлен как страховка (в новой сборке флаг уже не читается).

### B. Строгость селфтеста — решена фактом

Гейт смотрит только на артефакты (маркер ужатия, файл полного вывода, needle-факт), поэтому сборка с умирающими ходами проходила промоушен. Сейчас это неактуально: с выпиленной маской ladder-шаги проходят, и T1–T5 зелёные. Строгость («ненулевой код хода = провал») можно включать отдельным решением владельца — цепочка готова к этому.

## Дозор за апстримом (GHA + opencode) — работает

Регулярный workflow `.github/workflows/upstream-watch.yml` (arch-репо, cron `17 */6 * * *`):
внутри крутится **наш opencode** (форк `gpt-mem/opencode-mem`, линия `v2-base`), он изучает
новый релиз апстрима и собирает годное в форк. Три джобы:

| Джоба | Что делает | Токены |
|---|---|---|
| `collect` | дешёвый детектор на python: есть ли новый тег `v2.*`; без модели | не тратит, если новых тегов нет |
| `study` | opencode-сессия «изучить»: разбор диапазона по профилю продукта → отчёт + issue в форке | тратит |
| `port` | opencode-сессия «собрать»: cherry-pick PORT на `v2-base`, проверка профиля → черновик PR | тратит |

- Классификация: **PORT** (берём) / **ASK** (задевает наши правки → решает человек) / **SKIP** (мимо).
  Профиль продукта — `chain/upstream-policy.json` (`skip_paths`, `port_scopes`, `must_keep`, `must_not_return`).
- ASK автоматически не портится — только если человек написал «тянуть» в issue.
- Расхождение с апстримом считается по merge-base с апстримным HEAD (compare-по-файлам обрезается на 300 и шумит).
- Merge — за человеком; issue дозора ищется по точному префиксу заголовка `chore(upstream): порт <tag>`.

**Что починено в этом цикле** (arch PR #11–#21):

- Сборка форка под linux-x64 в GHA. Настоящая причина молчаливого падения — в `chain/build-fork-cli.sh`
  каталог форка оставался относительным, и поиск бинаря после `cd` уходил в `fork/fork/...`:
  сборка проходила, а бинарь не находился. Плюс `bun install` без `--os/--cpu` ставил только
  варианты текущей платформы, и в бинарь не попадал `@opencode-ai/pty-linux-x64-gnu`.
- Форковый composite-экшн `.github/actions/setup-bun` не переносится в наш workflow (требует
  `package.json` в cwd, падает на `Input required and not supplied: path`) — workflow переведён
  на `oven-sh/setup-bun@v2` (bun 1.4.2), сборка форка требует bun ^1.4.2.
- Сырьё `collect` теперь доезжает в `study` и `port` артефактом `upstream-collected`; раньше
  `$UPSTREAM_COLLECTED` указывал на несуществующий файл, и разбор шёл заново своим детектором

- Детектор кэшировал базу навсегда — следующий прогон разбирал бы уже слитый диапазон.
