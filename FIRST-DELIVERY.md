# Compact at first delivery (issue #23) — design

Дата: 2026-10-10. Статус: design для согласования (gate issue #23: не имплементировать до согласования). Ветка: cache-safe, `memory-context-v1`.

## 1. Проблема и цель

Замеры issue #20 (mimo-v2.6-flash): cache read ≈ 2.2% цены uncached input (~45×). Следствие: любая перезапись уже отправленной истории проигрывает — mid-turn компакция даже с батчами дала максимум −1.2% стоимости. Дефолт после PR #22 (граница на user-turn) корректен для кеша, но одноповоротные сессии не сжимаются вообще.

Единственный рычаг, снижающий **uncached** токены: не отправлять bulk больших tool-выводов в принципе — при первой доставке модели уходит компакт-маркер, полный оригинал уже лежит в SQLite (инвариант: оригиналы не трогаются; маркер несёт `call_id` + `retrieve=get_tool_call_details(...)`). Ожидаемый эффект на сценарии issue #20: uncached-приращения сжимаются ~16× на крупном чтении → **−70%+ реальной стоимости**, ноль инвалидаций кеша (проекция чисто append-only).

Это трек B0 из INTENT-CACHE-PLAN.md — база для всех дальнейших замеров.

## 2. Протокол маркера

Используем **ту же маркерную семантику**, что и историческая компакция: `[mem:compacted tool result]` / `[mem:compacted shell output]` с `kind/tool/command/call_id/status/preview/original/retrieve` (превью и сводки — через `PII.redact`, PR #18). Отличие только во **времени применения**: не «старые сообщения за границей», а «любой eligible-результат с момента первой отправки модели».

Обоснование одного словаря: путь ретрива, тесты, обучающий сигнал для модели идентичны; вторая маркерная разновидность — лишняя матриция.

## 3. Элигабельность (правила доставки)

Кандидат на delivery-маркер, если выполняется **всё**:

- tool state `completed` (ошибки, pending/running не трогаем — инвариант);
- не provider-executed, не memory-тул (`MEMORY_TOOL_PATTERN`);
- сериализованный output ≥ порога (дефолт 2000, env `OPENCODE_MEMORY_FIRST_DELIVERY_MIN_CHARS`);
- тул в allowlist. Дефолт: `bash` (shell + bash tool), `webfetch`, `websearch`, `read`. Env `OPENCODE_MEMORY_FIRST_DELIVERY_TOOLS` (comma-separated) переопределяет. `read` в дефолте, потому что файловые чтения доминируют в tool-heavy сессиях; если quality-тесты покажут деградацию edit-циклов — убрать `read` из дефолта (одна строка env, без перекодирования);
- shell-сообщение имеет `callID` (без пути ретрива не сжимаем — прежний инвариант).

## 4. Механика проекции (cache-safe)

Новый режим в `MemoryContext.project` / `projectV1`: при `OPENCODE_MEMORY_FIRST_DELIVERY=1` (дефолт off, требует включённого `OPENCODE_MEMORY_CONTEXT`) **логика границ не применяется** — compact-ится каждый eligible-результат на любой позиции, включая самый свежий.

Кеш-стабильность (почему это cache-safe):

- маркер — чистая функция от сохранённого оригинала → проекция истории на шаге N+1 даёт byte-identical префикс шага N плюс новый суффикс;
- результата, однажды доставленного полным текстом, в этом режиме не существует (он был маркером с первой доставки) → инвалидаций префикса ноль, чистый append-only;
- монотонность и идемпотентность тривиальны (проекция не хранит состояние).

Взаимодействие с флагами: `OPENCODE_MEMORY_MIDTURN`/`OPENCODE_MEMORY_BATCH_SIZE` в этом режиме неактуальны (они упорядочивают, КАКИЕ старые сообщения сжимать; здесь сжимается всё eligible) — остаются выключенными по умолчанию для cacheless-провайдеров. Режимы ортогональны, не смешиваются в одной сессии.

## 5. Контракт ретрива

Уже отгружено отдельным PR до этого дизайн-дока (PR #24, `Refs #23`):

- `get_tool_call_details(call_id, max_chars?, offset?, full?)` — V2 core + V1 opencode;
- `full=true` → полный payload до hard cap 200k chars; `offset` — постраничный доступ;
- `truncated=true` означает «есть контент за окном» + `total_chars` — модель листает, а не упирается в тупик;
- маркеры остаются с дефолтным `retrieve=get_tool_call_details(call_id="...")` — модель сама добавляет `offset`/`full` по мере надобности;
- оригинал по ретриву не редактируется (авторизованный точный доступ — инвариант #11/#18); превью в маркере редактируются.

До #24 извлечение 77KB-файла обрывалось на 8k без пути к остатку — это была реальная дыра ретрив-интегрити; теперь закрыта и для существующей исторической компакции.

## 6. Разрыв циклов (loop-breakers)

Риск: маркер вместо свежего результата → модель не видит содержимое → ре-читает файл → снова маркер → петля.

1. Маркер несёт head/tail-превью (400+200) + kind-сводку — для многих решений («команда упала? что в stderr хвосте?») retrieve не нужен.
2. Ретрив всегда возвращает **настоящий оригинал**, никогда маркер — шаг ретрива не зацикливается.
3. `full`/`offset` снимают главный ловушечный сценарий: постраничный проход через один и тот же вызов.
4. Quality-тест (см. §8) ассертит: needle-задача решается; число retrieve-вызовов ограничено; модель не повторяет идентичный bash/read подряд без причины.

## 7. PII/credentials

Без изменений относительно сложившегося: превью и сводки delivery-маркера проходят `PII.redact` (секреты, Bearer, карты, токены в URL); `pii=`-теги в маркере; оригинал в SQLite сырой; ретрив — авторизованный. Новых утечек доставка не добавляет: маркер строго меньше оригинала.

## 8. Приёмка и бенчмарки

Сценарии (issue #9 протокол, `benchmark run --opencode-session`, attach-pr к PR реализации):

1. **Одноповоротный сценарий issue #20** (3 файла по 77KB, needle в середине file2) — MEM off vs MEM on + FIRST_DELIVERY, идентичная модель/конфиг;
2. **Саммари-задача** ( summarizes tool-heavy сессию) — качество саммари без полных инлайнов.

Метрики: uncached input, cache read, provider-visible, **фактическая стоимость**, cache_hit_rate, число LLM-вызовов, успешность задачи, ретрив сжатого (needle найден).

Пороги приёмки: задача решается во всех руках (needle 100%), реальная стоимость **≥ −30%** к MEM-off baseline, uncached input существенно ниже (ожидание −70%+), инвалидаций кеша 0 (дебаг: префикс append-only).

## 10. Открытые вопросы

- Порог 2000 chars для первой доставки может быть агрессивным для мелких результатов, где инлайн дешевле retrieve-раунда — оставляем env-override, решение по замерам.
- `read` в дефолтном allowlist — под вопросом до quality-теста (§3).
- Провайдеры без prompt-cache (Trек A) — FIRST_DELIVERY им не вредит (нет кеша, который бы инвалидировать), но и MIDTURN им подходит; автоматический выбор режима по capabilities — отдельная работа (A1 в INTENT-CACHE-PLAN.md).
