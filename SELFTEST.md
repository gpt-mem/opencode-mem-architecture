# SELFTEST: dogfooding-сессия на нашей архитектуре

Дата: 2026-10-11. Роль: лучший дебагер — сессия сама работает на форке (`OPENCODE_MEMORY_CONTEXT=1`), тестирует свои тулы, PII, ретрив, кеш-метрики. Запускается периодически циклом (см. `~/.opencode/scripts/run-selftest.sh`).

## Принцип

Сессия получает промпт «ты на новой архитектуре» + репо, затем серию плотных ходов: инструменты → решение → PII-почта → плотные документы → 8–15 вопросов на ретрив. Финал — самоотчёт: какие тулы использовал, где ретрив понадобился, что сломалось.

## Ходы сценария (12)

**T1 — архитектура и тулы.** Ты работаешь на новой архитектуре MEM (форк OpenCode, репо gpt-mem/opencode-mem, ветка memory-context-v1). Self-review: посмотри какие инструменты доступны, особенно get_tool_call_overview / find_tool_calls / get_tool_call_details. Вызови get_tool_call_overview.
— Ожидание: модель видит memory-тулы, вызывает overview, возвращает JSON.

**T2 — решение.** Запиши решение: «принято решение форкать опенкод и его развивать» — сохрани через put_in_operational_memory (или ближайший доступный инструмент памяти).
— Ожидание: решение записано (если тул есть) или явно зафиксировано в тексте.

**T3 — PII-артефакт.** Вставлена почта: william.shekspier@gmail.com. Проверь через find_tool_calls / find_pii — появилась ли она в индексе артефактов?
— Ожидание: PII-тег/индекс находит почту; в маркерах она redacted.

**T4–T6 — плотные документы.** Три файла по ~8KB с needle-фактами (ID, строки, emails) вкладываются через --file.
— Ожидание: документы уходят в историю; при первой доставке большие куски получают маркеры (B0); originals в SQLite.

**T7 — ретрив решения.** Вспомни: какое решение ты записал? Используй тулы памяти для ретрива.
— Ожидание: через find/get details достаёт «форкать опенкод».

**T8 — ретрив PII.** Вспомни почту из документа 1.
— Ожидание: ретрив оригинала (PII не скрыта, доступна через authorized retrieval).

**T9 — дисковери.** Найди через find_tool_calls последние bash-вызовы с ошибкой (если были) или просто последние 5 tool-вызовов.
— Ожидание: компактный список call_id/status.

**T10 — детали по call_id.** Возьми любой call_id из T9 и достань детали через get_tool_call_details.
— Ожидание: оригинальный вывод (или offset/full если длинный).

**T11 — ретрив needle из документа.** Вспомни needle-факт из T4-документов (конкретный ID).
— Ожидание: модель либо помнит из префикса, либо достаёт через ретрив после компактации.

**T12 — финальный отчёт.** Самоотчёт: какие memory-тулы доступны, какие использовал, где понадобился ретрив, что сломалось/удивило. Оцени работает ли «сжимаем но ничего не прячем».
— Ожидание: структурированный отчёт.

## Что собирает раннер (после сессии)

1. Per-turn usage из SQLite: input/output/cache_read/cache_write, cost (лестница)
2. Debug-лог проекции: compacted=, protected_from= (B0-маркеры)
3. Список вызванных memory-тулов + их аргументы (из part表)
4. PII-теги в маркерах (redacted email)
5. Self-report модели из T12

## Порог приёмки

- memory-тулы видны и вызываются (T1, T9, T10)
- PII почта найдена/помечена (T3, T8)
- ≥1 успешный ретрив после компактации (T7/T11)
- usage показывает cache_read > 0 на стабильных ходах (кеш лестницы работает)
- финальный отчёт выдаётся
